## 3. 新 BUG 详单（按 GRE BUG 汇总格式）

### BUG-N1【严重·P1】隧道信息列表"收发字节数"恒为 0，不随真实流量更新（IKOS-7004 根因定位）

- **组件**：`ipsec2_tunnel.sh` `__show_list` / `ipsec2_tunnel_runtime` 临时表
- **优先级**：P1 ｜ **严重度**：严重
- **现象**：隧道信息页列表行 `in_bytes`/`out_bytes` 字段恒为 `"0"`，即使隧道刚跑过 5 包（420 字节）真实加密流量。
- **复现**：基底隧道建立 → router inner `ping -I 198.18.200.1 -c 5 198.18.200.2`（5/5 通）→ 调 `ipsec2_tunnel/show TYPE=list,list_total`。
- **实际结果**（铁证）：
  - API 行：`"in_bytes": "0", "out_bytes": "0"`
  - 同时刻 swanctl：`in ce53dc8c, 420 bytes, 5 packets` / `out c933fc82, 420 bytes, 5 packets`
  - 同时刻 `ip -s xfrm state`：`420(bytes), 5(packets)`
- **根因**：`__show_list`（line 269-272）从临时表 `ipsec2_tunnel_runtime` 读 `in_bytes/out_bytes`；该表由 `__load_runtime_query_table` 从 `__build_runtime_tunnels_json` 的快照填充，**该快照未调用 swanctl 实时计数**，故 in/out_bytes 永远是建链时的 0。只有 `TYPE=detail` 的 `__build_tunnel_detail_json`（line 317+，实时 `swanctl --list-sas`）才拿到真实计数。
- **影响**：用户在列表页看到的收发字节数永远是 0，无法判断隧道是否有流量，对应 IKOS-7004"收发数据包/字节/速率字段无统计"的现象层；本报告定位到**根因是 list 接口读静态快照而非实时计数**。
- **预期**：list 接口的 in_bytes/out_bytes 反映实时 swanctl/xfrm 计数，或字段标注"建链初值"。
- **验证标准**：打 N 包后 list 接口 in_bytes/out_bytes 与 swanctl 一致。

### BUG-N2【严重·P1】隧道详情抽屉"隧道SA""隧道统计"两个分区内容渲染为空（IKOS-7008 UI 侧）

- **组件**：前端 `/#/vpn/ipsecVpn` 隧道信息页"详情"抽屉
- **优先级**：P1 ｜ **严重度**：严重
- **现象**：点隧道行的"详情"，抽屉显示三个分区标题"隧道SA / 隧道统计 / 隧道信息"，但**"隧道SA"和"隧道统计"两个分区标题下是空白的**，只有"隧道信息"分区渲染了字段（隧道IP类型/协商方式/PFS/安全协议/互联信息/保护数据流）。
- **复现**：基底隧道建立+打流量 → 隧道信息页 → 点"详情" → 抓抽屉 DOM 文本 + 全页截图。
- **实际结果**（铁证）：
  - 后端 `TYPE=detail` API 返回完整 `statistics` 和 `sa` 对象（结构见 N9，含 traffic_rate/drop_overview/exception_analysis + SA 算法/寿命/SPI）。
  - UI 抽屉 DOM 全文（按"隧道SA/隧道统计/隧道信息"切分）：`"隧道SA": "", "隧道统计": ""` —— 两个分区**标题在但内容为空**。
  - 全页截图经图像分析复核：确认"隧道SA"和"隧道统计"标题下空白，仅"隧道信息"有内容。
- **根因**：前端详情抽屉组件未消费 `statistics`/`sa` 对象渲染（数据已到前端，渲染丢失）。这是 IKOS-7008"异常原因分析全量字段无统计"在 UI 层的真因——**后端给了数据，前端没画**。
- **影响**：用户无法在 UI 看到任何 SA 算法/寿命/收发统计/丢包分析，必须 SSH 查 swanctl。详情抽屉实际只显示了基础互联信息。
- **预期**：详情抽屉三分区均渲染后端返回的对应字段。
- **验证标准**：详情抽屉"隧道统计"显示与 swanctl 一致的收发字节/包数；"隧道SA"显示算法/寿命/剩余时间。
- **注**：即便前端修复渲染，统计数值仍可能因 N8（child 取样）和 N9（字段硬编码0）失真，需一并处理。

### BUG-N3【一般·P2】SA 流量上限配置为 0（不限）时，详情显示固定 1843200 而非"不限"

- **组件**：`ipsec2_tunnel.sh` `__build_tunnel_detail_json`（line 685-687）
- **优先级**：P2 ｜ **严重度**：一般
- **现象**：策略 `ipsec_sa_bytes=0`（表示不限流量），但详情接口返回 `ipsec_sa_lifetime_bytes=1843200`、`remaining_ipsec_sa_lifetime_bytes=1843200`，UI 详情会显示"1843200/600"而非"不限"。
- **复现**：基底策略 sa_bytes=0 → 调 `TYPE=detail`。
- **实际结果**：`ipsec_sa_lifetime: "1843200/600"`，`ipsec_sa_lifetime_bytes: 1843200`（配置是不限）。
- **根因**：line 686-687：`local configured_bytes = num(policy.ipsec_sa_bytes, 0); if configured_bytes <= 0 then configured_bytes = 1843200 end` —— **把"0=不限"硬编码覆盖成 1843200KB(1.76GB)**，且剩余字节也按这个假上限算。
- **影响**：用户配置"不限流量"，UI 却显示一个 1.76GB 的上限和倒计，误导用户以为流量有上限；剩余字节数值无意义。
- **预期**：sa_bytes=0 时详情显示"不限/永久"，不显示假上限。
- **验证标准**：sa_bytes=0 时 `ipsec_sa_lifetime_bytes` 为 0 或文本"不限"，剩余不倒计。

### ~~BUG-N4~~【已撤销·复现证伪】PSK 不匹配失败时，UI 日志诊断误报"对端主动断开"

> **2026-07-23 二次复现后撤销本条。** 初次记录系场景混淆：在 terminate（触发 DELETE）之后调 `TYPE=log`，诊断如实返回了"隧道释放/对端主动断开"（因 terminate 确实发了 DELETE），却被误记为"PSK 不匹配被误诊"。
>
> **二次复现（连续 2 次）铁证**：PSK 不匹配场景下，诊断接口**正确**返回 `phase=认证阶段 / failure_reason=身份认证失败 / reason_desc=本端与对端认证参数不一致，常见原因是预共享密钥、本端 ID 或对端 ID 配置错误`，与 charon 真实日志 `N(AUTH_FAILED)` 完全吻合。三个场景对照均准确：
> - PSK 不匹配 → "身份认证失败"（准确）
> - 隧道已建立 → "当前隧道已建立"（正常）
> - terminate/DELETE → "隧道释放/对端主动断开"（准确，非误诊）
>
> **结论：诊断引擎工作正确，能区分认证失败/正常/隧道释放三类状态。本条撤销，不计入新 BUG。**

### BUG-N5【严重·P1·安全】DPD 配置的 dpd_timeout 被静默放大（30s→100s），与用户配置不符

- **组件**：`ipsec2_common.sh` `__ipsec2_effective_dpd_timeout`（line 410-423）
- **优先级**：P1 ｜ **严重度**：严重（安全相关）
- **现象**：策略配置 `dpd_timeout=30`，但生成的 swanctl.conf 实际写入 `dpd_timeout = 100s`，DPD 失效检测时间被静默放大约 3 倍。
- **复现**：基底策略 dpd_interval=10/dpd_timeout=30 → 查 `/etc/swanctl/conf.d/ipsec2-*.conf`。
- **实际结果**（铁证）：
  - DB：`dpd_timeout = 30`
  - swanctl.conf：`dpd_delay = 10s` / `dpd_timeout = 100s`
- **根因**：line 416-418：`if [ "$timeout" -lt 60 ]; then timeout=$((delay + timeout * 3)); fi` —— 用户设 30(<60) 被改成 `10 + 30*3 = 100`。且 `[ "$timeout" -lt 60 ] && timeout=60` 二次兜底。**配置值与生效值不符，UI 不提示**。
- **影响**：用户期望对端失效 30s 内检测，实际需 ~100s；安全/容灾切换延迟显著大于预期。与 IKOS-7009"SA 生存时间与剩余生存时间数值异常(配置不符)"同类（配置值不等于运行值）。
- **预期**：要么尊重用户配置的 dpd_timeout，要么 UI 明示"已自动调整为 Xs"。
- **验证标准**：swanctl.conf 的 dpd_timeout 等于 DB 配置值，或 UI/校验提示调整。

### BUG-N6【严重·P0·疑似功能失效】DPD 在对端长时间黑洞(>160s)下未触发失效检测，SA 始终 ESTABLISHED

- **组件**：strongSwan charon DPD 调度 / `ipsec2` DPD 配置下发
- **优先级**：P0 ｜ **严重度**：阻断（待开发确认是否预期）
- **现象**：dpd_enabled=yes/dpd_interval=10/dpd_timeout=30(生效100)/dpd_action=restart，对端 iptables 全 DROP router 的 IKE/ESP 包持续 **160 秒**（远超生效 timeout 100s），router 侧 IKE SA **始终 ESTABLISHED，从未被判定失效或 restart**。
- **复现**：基底隧道 → peer `iptables -I INPUT -s 10.66.0.150 -j DROP` → 每 10s 查 router `swanctl --list-sas`，连续 160s。
- **实际结果**（铁证）：
  - t=10s ~ t=160s：router SA 全程 `ESTABLISHED`，无任何状态变化、无 DELETE、无 restart。
  - 黑洞 30s 窗口内：仅 **1 次** `sending DPD request`，随后 charon 进入 retransmit（`retransmit 1/2 of request with message ID 10`），未按 dpd_delay=10s 周期发新 DPD。
  - 黑洞期间甚至有 `received retransmit of request with ID 8, retransmitting response`（对端仍在对某些旧请求重传响应，疑似保活干扰）。
- **根因（初步）**：DPD 仅在"无任何待处理任务"时按 dpd_delay 调度；一旦进入 retransmit 循环，DPD 计时被压制，且 `dpd_action=restart` 未在 timeout 后真正执行。需开发确认 strongSwan DPD 调度与 ipsec2 的 `start_action`/`retransmit_timeout` 联动是否正确。
- **影响**：**对端真实宕机/链路中断时，主路由 SA 长期不收敛**，依赖 DPD 快速切换的容灾/负载场景失效。这是比 BUG-N5 更严重的问题——即便 timeout 被放大到 100s，160s 仍未触发，说明 DPD 检测链路本身可能失效。
- **预期**：对端黑洞超过生效 dpd_timeout 后，SA 应被 DELETE 并按 dpd_action=restart 重新发起。
- **验证标准**：黑洞 >生效timeout 后 router SA 在 ±20s 内转为 CONNECTING/重建。
- **注**：本结论基于 iptables DROP 模拟链路中断；建议开发补充真实断网/接口 down 复测确认。

### BUG-N7【一般·P2】策略名称(tagname)后端上限 15，前端无长度限制，超长仅报"参数错误"无长度提示（IKOS-6950 量化）

- **组件**：前端新建策略 tagname 输入框 / 后端 `check.lua M.tagname` / `ipsec2_common.sh __check_param_add`
- **优先级**：P2 ｜ **严重度**：一般
- **现象**：UI 新建策略时 tagname 输入框 **无 maxlength 限制**（实测 `maxlength: null`），用户可输入任意长度；后端实际只接受 1-15 字符，超长保存被拒且只报通用 `参数错误: tagname`，不提示是长度超限。
- **复现**：
  - UI：新建策略 → 检查 `#tagname` input `maxlength` 属性 = null。
  - 后端 Lua 直测 `check.tagname`：len 1-15 ACCEPT，len 16+ REJECT；首字符 `_`/`-` 拒；空格拒；中文按 unicode_len 计。
- **实际结果**（铁证）：
  - 前端：tagname maxlength=null（无限制）
  - 后端 M.tagname：`len=15 → ACCEPT`，`len=16 → REJECT`，错误信息仅 `参数错误: tagname`
- **根因**：前后端未共享校验规则。后端 `M.tagname` 限 `len>=1 and len<=15`（旧 .bak 是 46，现固件收紧到 15），前端未同步。
- **影响**：用户输 16+ 字符的策略名，保存被拒且不知原因（以为是字符问题），反复试错。关联 IKOS-6950"策略名称格式错误提示需修改"——本报告**量化了 15 字符上限**并定位前后端不一致。
- **预期**：前端 tagname maxLength=15，或后端错误信息含"长度需 1-15"。
- **验证标准**：16 字符名前端即拦截并提示长度上限。

### BUG-N8【严重·P1】隧道详情统计受 child SA 取样影响，多 child 残留时显示 0/失真

- **组件**：`ipsec2_tunnel.sh` `__show_detail` / `__build_runtime_tunnels_json(selected_key)`
- **优先级**：P1 ｜ **严重度**：严重
- **现象**：`TYPE=detail` 的收发字节/包数只统计 `tunnel_key` 选中的那一个 child SA；当隧道存在多个 child（rekey 残留，实测常驻 2 个），若选中的是空闲 child，detail 返回全 0；同一隧道打同样流量，不同时刻查 detail 数值不稳定。
- **复现**：基底隧道 → 打 5 包流量 → 同时刻对比 swanctl 与 detail API。
- **实际结果**（铁证，同一时刻）：
  - swanctl 显示 2 个 child：`#93: 0 bytes/0 packets`（空闲残留）、`#94: 420 bytes/5 packets`（活跃）
  - list 返回 `tunnel_key=ipsec2-spoke-1#57` 对应 child `esp{93}`（计数 0 的那个）
  - detail 查该 tunnel_key：`in_protected_bytes=0, out_protected_bytes=0, in_protected_packets=0` —— **取到了空闲 child，显示 0**
  - 而真实活跃 child #94 有 420/5（用户手动查到活跃 child 时能看到 10/840，故不同人/不同时刻看到不同值）
- **根因**：`__show_detail`（line 282-317）用 `selected_key` 过滤 runtime_json，`__build_tunnel_detail_json` 的 `sum_child` 只在选中 child 内对 esp/ah 多协议求和，**不跨所有 child 累加**。配合多 child 残留（rekey 不清旧 child），统计取样失真。
- **影响**：用户看到的收发统计可能恒为 0（取到空闲 child）或数值跳变，无法准确反映隧道真实流量。这是 IKOS-7004"统计不准"的另一根因（除 N1 的 list 静态快照外，detail 的取样也有问题）。
- **预期**：detail 统计应累加该 IKE SA 下所有活动 child 的计数（或明确标注"当前 child #N"）。
- **验证标准**：打 N 包后，无论 list 选中哪个 child，detail 的收发字节/包数与 swanctl 全 child 求和一致。

### BUG-N9【严重·P1】隧道统计大量字段硬编码为 0，速率/出方向丢包/细分丢包原因均未实现统计（IKOS-7004/7008 根因）

- **组件**：`ipsec2_tunnel.sh` `__build_tunnel_detail_json`（line 800-820）
- **优先级**：P1 ｜ **严重度**：严重
- **现象**：`TYPE=detail` 的 `statistics` 对象中，除受保护数据包/字节（`in/out_protected_packets/bytes`）动态有值外，**速率字段、出方向丢包、8 类细分丢包原因全部恒为 0**，无论怎么打流量/丢包都不会有值。
- **复现**：基底隧道 + 打流量 → 调 `TYPE=detail` → 看 `statistics` 全字段。
- **实际结果**（铁证，源码 line 800-820）：
  ```
  traffic_rate:
    in_protected_packets = sum_child("in_packets")   ← 动态，有值
    out_protected_packets = sum_child("out_packets") ← 动态，有值
    in_protected_bytes = sum_child("in_bytes")       ← 动态，有值
    out_protected_bytes = sum_child("out_bytes")     ← 动态，有值
    in_packet_rate  = 0   ← 硬编码，永远 0
    out_packet_rate = 0   ← 硬编码，永远 0
    in_byte_rate  = 0     ← 硬编码，永远 0
    out_byte_rate = 0     ← 硬编码，永远 0
  drop_overview:
    in_dropped_packets = state_failed          ← 动态(xfrm failed)，需攻击场景
    out_dropped_packets = 0                    ← 硬编码，永远 0
    replay_dropped_packets = replay_drop       ← 动态(xfrm replay)，需重放攻击
  exception_analysis:
    sa_not_found.../invalid_length.../auth_failed.../encap_failed.../
    decap_failed.../post_decap.../mtu_check.../local_process_limit.../
    crypto_rate_limit... = 0                   ← 这 8 项硬编码，永远 0
    sa_error_dropped_packets = state_failed    ← 动态，与 in_dropped 同源
  ```
- **根因**：源码 line 800-820 直接把 `in_packet_rate/out_packet_rate/in_byte_rate/out_byte_rate/out_dropped_packets` 及 exception_analysis 的 8 项赋值为字面量 `0`，从未实现计算逻辑。`replay_drop`/`state_failed` 虽动态读 xfrm，但需构造重放/坏包攻击才能非 0，正常使用恒 0。
- **影响**：UI 详情（即便 N2 修复渲染后）显示的速率永远是 0（用户无法看实时速率）、出方向丢包永远 0、细分丢包原因永远 0，失去诊断价值。直接对应 IKOS-7004"收发数据包/字节**速率**字段无统计"和 IKOS-7008"异常原因分析**全量字段**无统计"。
- **预期**：速率字段基于两次采样差值计算；细分丢包原因从 xfrm/ethtool/charon 对应计数器读取。
- **验证标准**：高速打流量后 in/out_packet_rate > 0；构造重放后 replay_dropped > 0；各丢包原因能反映真实事件。
- **注**：`replay_drop`/`state_failed` 字段本轮因 peer 为 busybox（无 tcpreplay/python3）无法构造重放/坏包攻击复现非 0，但其动态读 xfrm 的逻辑已由源码确认，非硬编码。

## 4. 已知 BUG 铁证复现（非新单，附证据）

### BUG-008 复现：协议版本不一致后，对端残留半开 IKE SA 且不超时清理

- **前置**：基底隧道（IKEv2 双端）。
- **复现**：双端 terminate → 改 peer 为 IKEv1（路由器仍 IKEv2）→ reload → peer 发起（失败）。
- **铁证**：
  - router：SA=NONE（清理正确）
  - **peer：残留 `ipsec2-spoke-1: #40, CONNECTING, IKEv1, ... active: ISAKMP_VENDOR MAIN_MODE`**（半开 IKE SA）
  - 连续 3 次失败发起：peer SA 数=1（不堆积，strongSwan 复用同一 CONNECTING SA，queued QUICK_MODE 增至 10）
  - **等 60s 后 peer SA 数仍=1**：半开 SA **不超时清理**，长期残留。
- **结论**：BUG-008 在当前固件（FIRMWAREID=10002）**仍可复现**，且补充了"半开 SA 不超时"这一更严重的现象（原 BUG-008 仅记"保留单侧 IKE SA"）。建议升级 BUG-008 严重度或补充"超时清理缺失"子项。

> 补充观察：router 单端 `swanctl --terminate` 后，因 `start_action=start`(auto)，router 会立即自动重连，掩盖了"对端是否感知"的检测——这解释了为何现有综合用例的残留审计在主路由侧通过而对端侧未覆盖。

## 5. 边界值与校验内部不一致（观察项，非用户 BUG）

### 5.1 后端两层校验内部不一致（`ipsec_sa_bytes` / `ipsec_sa_idle`）

- `__check_param_add`（varl_json 层）：`ipsec_sa_bytes >= 0 and <= 4294967295`、`ipsec_sa_idle >= 0 and <= 86400`
- `__validate_policy_constraints`（约束层）：`ipsec_sa_bytes > 0 且 < 2560 拒`、`ipsec_sa_idle > 0 且 < 60 拒`
- **实际有效范围**：sa_bytes = 0(不限) 或 2560-4294967295（1-2559 是死区）；sa_idle = 0(禁用) 或 60-86400（1-59 是死区）
- 前端 placeholder 与**约束层**一致（`2560-4294967295`、`60-86400`），故对用户**不构成 BUG**，但两层校验规则不自洽，维护易踩坑。建议合并为单一规则源。

### 5.2 已量化边界（铁证）

| 字段 | 后端有效范围 | 前端 placeholder | 一致性 |
|---|---|---|---|
| tagname | 1-15 字符（中文按 unicode_len） | 无限制 | ❌ 不一致（BUG-N7） |
| secret(PSK) | 1-128 字符 | 无限制 | ❌ 不一致（BUG-010 已记） |
| ipsec_sa_time | 180-604800 秒 | 180-604800 | ✅ 一致 |
| ipsec_sa_bytes | 0 或 2560-4294967295 | 2560-4294967295 | ✅ 一致（0=不限特殊） |
| ipsec_sa_idle | 0 或 60-86400 | 60-86400 | ✅ 一致（0=禁用特殊） |
| dpd_timeout | 1-900（但 <60 静默转换） | 无限制 | ❌ 不一致（BUG-N5） |

## 6. 附带观察（PSK 模式 CERTREQ，备查）

- **现象**：IKEv2 PSK 认证的 IKE_AUTH 阶段，peer charon 日志显示 `sending cert request for "C=US,O=Entrust..."` 等约 **18 条 CERTREQ**（Entrust/COMODO/GoDaddy/CFCA/GDCA 等受信 CA 根）。
- **影响**：纯 PSK 隧道无需证书，发送 CERTREQ 增加 IKE_AUTH 报文体积（实测请求包 1236 字节，部分来自这些 CERTREQ），属 strongSwan 默认 `send_certreq=yes` 行为。
- **建议**：PSK-only 连接设 `send_certreq=no`，减小协商报文、避免泄露本机受信 CA 列表（信息泄露）。**判定为优化项，非阻断 BUG**。
