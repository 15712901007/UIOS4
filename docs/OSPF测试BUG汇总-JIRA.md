## OSPF-1【严重·Critical】保存/reload 失败后 DB 或活动配置已部分提交，且没有原子回滚

### 问题摘要

OSPF 实例、区域接口、接口参数或路由引入执行新增/编辑时，接口返回 HTTP 200、业务码 `2031` 和“操作失败/reload failed”，但数据库或 FRR 活动配置已经发生部分变化。失败后系统没有把 DB、生成配置和 daemon 运行态恢复到操作前状态，形成 UI、API、DB、配置和运行态不一致。

### 前置条件

1. 设备已进入 OSPF 页面。
2. 使用未占用的实例号、Router ID 和测试区域。
3. 记录操作前全部 OSPF 业务表、生成配置哈希、活动配置哈希和 daemon 运行配置。

### 复现步骤

1. 通过 UI 新建 OSPFv2 实例并保存。
2. 进入实例详情，新建 Normal 区域并绑定一个可用接口。
3. 设置合法的 network type、priority、cost、Hello 和 Dead 参数后保存。
4. 或通过 UI 新建 connected 路由引入并保存。
5. 记录页面提示及真实 API 响应。
6. 在失败响应后立即比较操作前后的相关 DB 表、`/tmp/ospf.frr`、`/etc/frr/frr.conf` 和 daemon 实际运行配置。

### 实际结果

- HTTP 状态为 200，但业务码为 `2031`，页面显示操作失败或 reload failed。
- 部分场景中 DB 已新增或修改记录。
- 部分场景中活动配置已经变化，但生成配置、活动配置和 daemon 实际加载内容不一致。
- daemon 没有完整加载区域/接口命令，页面保存链路最终失败。
- 产品没有自动恢复失败前的 DB 和活动配置，后续操作会建立在不一致状态上。

### 预期结果

保存和 reload 应满足事务一致性：

1. 校验、生成配置和 daemon 语法/加载全部成功后，才提交 DB 和活动配置；或
2. 任一环节失败时，DB、生成配置、活动配置和 daemon 运行态全部回滚到操作前状态；
3. API 返回值必须准确说明是否已提交、是否已回滚以及失败环节；
4. UI 不得把 HTTP 200 当作业务成功，也不得在失败后回显未真正生效的配置。

### 影响

- 用户无法判断配置是否真正生效。
- DB 与实际协议运行态可能长期不一致。
- 后续编辑、删除、启停、恢复和路由收敛都可能基于错误状态。
- OSPF 属于核心路由协议，该问题可能影响邻接、路由传播及业务转发，建议作为最高优先级修复。

### 开发定位建议

- 检查 `ospf.sh` 的 add/edit → DB 更新 → 配置生成 → 配置替换 → reload 调用顺序。
- 检查 `/tmp/ospf.frr` 到 `/etc/frr/frr.conf` 是否采用语法校验通过后的原子替换。
- 在调用 FRR reload 前保存可恢复快照，reload 失败后定向恢复原记录和旧活动配置。
- 区分 HTTP 状态、业务状态和 reload 结果，禁止以 HTTP 200 表示保存成功。
- 增加失败注入测试：配置生成失败、语法检查失败、daemon 拒绝、reload 中断时均不得留下部分状态。

### 验收标准

- 相同场景连续执行至少 20 次，无 DB/配置/daemon 分叉。
- 任意失败注入后，相关表结构化差异为空，活动配置与操作前语义一致。
- 保存成功时 DB、生成配置、活动配置和 daemon 运行配置逐字段一致。
- 保存失败时邻居、LSDB、RIB/FIB 和非目标 OSPF 配置不发生意外变化。

## OSPF-2【严重·Critical】OSPFv3 区域接口 API 返回 3001，页面无法形成可运行配置

### 问题摘要

OSPFv3 实例记录可以写入，但通过页面新增 IPv6 区域并绑定接口时，`area_interface` 保存返回业务码 `3001` 和“请求参数不合法/operation failed”。数据库不产生区域与接口关联，生成配置和 daemon 不包含对应 OSPFv3 接口区域命令，导致 OSPFv3 页面功能不可用。

### 复现步骤

1. 进入 OSPF 页面，新建 OSPFv3 实例。
2. 填写合法实例号和 Router ID 并保存。
3. 进入该实例的区域详情，新建 Normal 区域 `0.0.0.0`。
4. 选择一个具备 IPv6 链路本地地址的 UP 接口。
5. 使用页面默认的 broadcast、priority、cost、Hello、Dead 参数保存。
6. 检查 API 响应、`ospf_area`、`ospf_interface_attr`、生成配置和 FRR 运行配置。

### 实际结果

- OSPFv3 实例写入后，区域接口请求返回 HTTP 200、业务码 `3001`。
- 响应语义为请求参数不合法/operation failed。
- DB 不生成 IPv6 区域与接口关联。
- 生成配置缺少接口区域绑定，daemon 运行配置也没有对应命令。
- UI 无法建立 OSPFv3 邻接、LSDB、RIB/FIB 和真实 IPv6 流量链路。

### 排除项

- 同一物理接口和对端环境通过脱离 UI 的透明运行态诊断，可以建立双向 Full 邻接。
- 已实际验证 IPv6 LSDB、随机 `/128` OSPF 路由和真实 IPv6 流量正常。
- 因此不是物理链路、FRR OSPFv3 能力或测试拓扑不支持，故障位于产品 UI/API/DB/配置生成链路。

### 预期结果

- 页面提交的 OSPFv3 区域和接口参数应通过 API 校验。
- DB 应生成正确的 IPv6 区域、接口属性及关联键。
- 生成配置和 daemon 应加载对应接口、area、instance-id、timer、cost 和 priority。
- 页面保存成功后应能通过真实 OSPFv3 邻接、LSDB、RIB/FIB 和流量验证。

### 开发定位建议

- 核对 `address_family=ipv6`、`process_id`、`area_id` 和 `interface_attrs` 的参数解析。
- 核对 OSPFv3 `process_id` 到接口 `instance-id` 的映射。
- 核对 FRR 7.5 所需的 interface 模式参数和 `router ospf6` 下接口区域绑定语法。
- API 参数错误响应应指出具体字段，不能只返回笼统的 3001。

### 验收标准

- OSPFv3 实例、区域和接口可以完全通过 UI 新建、编辑、停用、启用和删除。
- UI 保存后 DB、配置和 daemon 一致。
- 独立对端能够达到 Full，路由可学习、撤销和恢复，真实 IPv6 流量形成控制闭环。

## OSPF-3【高·Major/Security】OSPF 认证输入框使用明文 text 且没有 maxlength

### 问题摘要

OSPF 接口认证字段在页面 DOM 中为普通 `text` 输入框，输入内容直接可见；同时控件没有 `maxlength`，页面也没有明确展示最大长度约束。

### 复现步骤

1. 进入任一 OSPF 实例的区域/接口编辑页面。
2. 选择页面支持的认证模式。
3. 定位认证输入框并输入任意测试值。
4. 检查输入框类型和 maxlength 属性。

### 实际结果

- 输入框类型为 `text`，内容明文显示。
- DOM 中不存在有效的 `maxlength`。
- 用户无法在提交前得知长度边界，超长输入的拒绝层级不明确。

### 预期结果

- 认证值输入框应使用受保护的密码控件，默认遮罩显示。
- 如提供“显示/隐藏”按钮，应默认隐藏并由用户主动切换。
- 页面、API 和底层配置生成应使用一致的最大长度与字符集约束。
- 错误提示不得回显认证原值。
- 日志、响应、报告、截图、trace 和异常信息中不得包含认证原值。

### 影响

- 存在现场旁观、录屏、截图和 DOM 采集泄漏风险。
- 无 maxlength 可能导致 UI 与 API 校验不一致或超长值进入后端处理链路。

### 验收标准

- 默认遮罩，认证值不可通过普通页面文本直接观察。
- maxlength 与 API/daemon 实际限制一致。
- 边界值、越界值和非法字符均给出明确且不泄密的错误提示。
- 自动化敏感信息审计确认 HTML、JSON、Excel、日志和截图中不存在认证原值。

## OSPF-4【中·Major】页面声明 cost=0 合法，但 API 以“参数错误: cost”拒绝

### 问题摘要

OSPF 接口表单的占位/范围提示声明 cost 支持 `0..65535`，但设置 cost=0 保存时，API 返回“参数错误: cost”。页面约束与后端校验规则不一致。

### 复现步骤

1. 新建或编辑一个 OSPF 区域接口。
2. 其他字段填写合法值。
3. 将协议开销 cost 设置为 0。
4. 提交保存并记录页面校验和 API 响应。

### 实际结果

- 浏览器和页面校验允许输入 0。
- API 拒绝请求并返回 cost 参数错误。
- 用户只能在提交后才知道页面展示的合法值实际不可保存。

### 预期结果

页面、API、DB 和 FRR 语义必须一致：

- 如果产品定义 cost 最小值为 1，页面应显示并校验 `1..65535`；
- 如果产品定义允许 0，API 和配置生成必须接受并按产品语义处理 0；
- 不得出现页面允许、API 拒绝的矛盾行为。

### 验收标准

- 最小值、最大值和两个越界值在页面/API 层得到一致结果。
- 合法边界能够保存并正确映射到 DB、生成配置和 daemon。
- 非法边界被拒绝且 DB、配置和运行态不变化。

## OSPF-5【中·Major】修改后的 OSPF 表单取消时直接丢弃内容，没有二次确认

### 问题摘要

用户修改 OSPF 实例或区域接口表单后，点击“取消”或关闭 Drawer，页面直接关闭并丢弃全部未保存内容，没有“继续编辑/确认放弃”的二次确认分支。

### 复现步骤

1. 进入 OSPF 新建或编辑 Drawer。
2. 修改 Router ID、区域类型、接口参数或其他字段。
3. 点击“取消”或关闭按钮。

### 实际结果

- Drawer 立即关闭。
- 不出现继续编辑/确认放弃提示。
- 本次修改没有发送保存 API，DB 保持不变，但用户输入不可恢复。

### 预期结果

- 未修改表单可以直接关闭。
- 已修改表单关闭时应弹出二次确认。
- “继续编辑”应保留全部输入并返回表单。
- “确认放弃”才关闭表单，且不发送保存请求、不修改 DB。

### 影响

- 复杂 OSPF 区域、接口和认证参数可能因误操作全部丢失。
- 在多区域、多接口配置场景中重新填写成本较高。

### 验收标准

- 脏表单可稳定区分继续编辑和确认放弃两个分支。
- 继续编辑后所有字段保持原值。
- 确认放弃后 API、DB、配置和 daemon 均无变化。

## 不应提交为产品 BUG 的事项

以下项目有完整证据，但不属于 OSPF 产品缺陷：

1. **三节点独立 transit 不通**：动态 tagged VLAN 两端接口均 UP，但双向均无报文接收；对端 LAN1 物理链路为 down，属于外部交换/物理链路限制。
2. **DR/BDR 不可验证**：当前三台设备无法加入同一个可用广播 VLAN，缺少第三广播节点。
3. **ECMP 不可验证**：没有两条独立等价数据面路径。
4. **多区域 ABR 和三节点双向 L5 不可验证**：受独立 transit 物理链路阻塞，禁止使用管理网伪造。
5. **页面没有搜索、刷新、帮助、复制、批量、导入导出等入口**：DOM、页面路由和真实接口均未发现这些功能，已标记不适用，不能按缺陷提交。
6. **透明 vtysh 运行态诊断**：只用于证明 daemon 和拓扑具备 OSPFv2/OSPFv3 能力，不代表 UI 保存成功，也不是绕过缺陷后的通过结果。
7. **此前管理路由偶发消失**：OSPF 测试没有在管理网启用协议、没有修改管理默认路由，finally 后无 OSPF 路由或测试对象残留；现有证据不足以归因于 OSPF。

## 测试覆盖及恢复结论

- OSPFv2：双向 Full、LSDB、`proto ospf` 路由、协议 89 和真实流量已验证。
- 认证负向：认证不匹配后邻接/路由/流量撤销，恢复后重新收敛。
- 宣告撤销：测试前缀撤销和恢复形成完整控制闭环。
- 实例生命周期：down/up 后 DB、邻接和路由按预期撤销及恢复。
- OSPFv3：透明诊断下双向 Full、IPv6 LSDB、随机 `/128` 路由和真实 IPv6 流量已验证；UI 保存仍保持失败。
- finally 和独立残留审计通过：无测试实例、区域、接口属性、路由引入、测试 VLAN、临时 daemon、协议 89 规则或 OSPF 路由残留。
