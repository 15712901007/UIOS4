# 【网络配置-IP/MAC限速】下行实测带宽约为配置值的 50%，独立/共享限速均复现

## Jira 基本信息

- **问题类型**：Bug
- **模块**：网络配置 → IP 限速 / MAC 限速；底层 `ik_core`、`byteslimit`、`bytesband`
- **建议优先级**：High / P1
- **复现概率**：100%（本轮 IP/MAC × 独立/共享共 4 个下行场景全部复现）
- **影响**：下行可用带宽仅约为用户配置值的一半，且页面、数据库和 iptables 均显示配置正确，用户难以从配置层发现异常

## 测试环境

- 被测路由器：`10.66.0.45`
- 架构/内核：`aarch64 / Linux 5.10.194`，内核构建时间 `2026-07-17`
- 测试客户端：`10.66.0.18`，LAN 地址 `192.168.148.2`，接口 `ens11`
- iperf3 服务端：`10.66.0.40:5201`
- 测试日期：`2026-07-29`
- 容差标准：配置目标的 `±20%`

## 前置条件

1. IP/MAC 限速数据库和运行时链无残留。
2. 客户端到 iperf3 服务端的流量经过被测路由器。
3. 建规则前分别测量相同方向、相同并发流数量的未限速基线。
4. 限速值按未限速基线约 45% 动态选择，确保链路能力明显高于配置上限，排除物理链路跑不满造成的假象。

## 复现步骤

### 场景一：IP 独立限速

1. 新建 IP 限速规则，目标 IP 为 `192.168.148.2`，模式选择“独立限速”。
2. 配置上行 `52608 KB/s`、下行 `22528 KB/s`。
3. 确认数据库字段、IP_QOS 上下行规则、ipset 和 `ik_core` 均正常。
4. 执行单流 iperf3：

   ```bash
   iperf3 -c 10.66.0.40 -B 192.168.148.2 -t 10 -O 2 -J -p 5201
   iperf3 -c 10.66.0.40 -B 192.168.148.2 -t 10 -O 2 -J -p 5201 -R
   ```

### 场景二：IP 共享限速

1. 删除独立限速规则并确认无残留。
2. 新建同一目标 IP 的“共享限速”规则。
3. 配置上行 `52608 KB/s`、下行 `20224 KB/s`。
4. 使用 `-P 4` 执行 4 条并发流，验证共享桶的聚合吞吐。

### 场景三、四：MAC 独立/共享限速

使用客户端 `192.168.148.2` 对应网卡 MAC 创建 MAC 限速规则，分别选择独立和共享模式，重复相同的基线与单流/4 流验证。

## 期望结果

1. 上下行实测带宽应落在配置值的 `±20%` 区间内。
2. 共享限速 4 条并发流的**聚合带宽**应落在共享配置值的 `±20%` 区间内。
3. IP 限速与 MAC 限速的数据面结果应与数据库和 iptables 中的限速值一致。

## 后端证据

### 已证实

1. **GUI/数据库数值正确**：L1 查询得到的 `upload`、`download`、`type` 与页面配置一致。
2. **规则确实生效**：IP_QOS/MAC_QOS 中能按规则 ID、方向和速度找到对应规则，ipset 包含目标 IP/MAC，`ik_core` 已加载。
3. **不是规则重复挂载**：

   ```text
   -A FORWARD -j IP_QOS
   -A FORWARD -j MAC_QOS
   ```

   两条自定义链在 FORWARD 中均只有 1 个引用。

4. **不是 shell 除以 2**：`simple_qos.sh` 和 `mac_qos.sh` 均把数据库中的 `$download` 原样传入内核扩展：

   ```bash
   # 独立限速
   -m byteslimit --byteslimit $download --byteslimit-mod dstip \
     --byteslimit-name simpledown$id -j DROP

   # 共享限速
   -m bytesband --bytesband $download \
     --bytesband-name simpledown$id -j DROP
   ```

   MAC 限速使用相同机制，只是桶名为 `macdown$id`。

5. **不是 HTB 队列整形**：lan1/wan1 当前没有 HTB class；IP/MAC 限速通过 FORWARD 链的令牌桶匹配后直接 `DROP` 实现。
6. **GRO/GSO 已开启**：`eth0`、`lan1`、`wan1` 的 GRO/GSO 均为 on，下载方向可能在聚合 skb 上进入自定义计量逻辑。

### 根因判断

问题责任层已定位到 `ik_core` 提供的 `byteslimit/bytesband` 下载数据面，而不是 GUI、数据库、规则生成或 iptables 挂载。

高概率由以下两个因素共同造成：

1. **机制问题**：当前实现是 policer（超令牌后 DROP），不是 shaper（队列整形）。TCP 遭遇周期性丢包后会触发拥塞窗口退避，因此有效吞吐可能明显低于配置上限。
2. **下载方向计量异常**：单纯 policing 不能充分解释“IP/MAC、独立/共享均约为 50%，但上行正常”的稳定方向差异。需重点检查 `dstip` 下载路径是否在 GRO/GSO skb、fastpath/slowpath 切换或 skb 分段过程中重复扣减令牌/按错误长度计费。

目前可以确定责任层，但在没有 `ik_core` 源码打点前，不能声称已经定位到具体代码行。

## 开发排查建议

1. 在 `byteslimit` 和 `bytesband` 的 token 扣减处打印或统计：
   - hook、方向、桶名；
   - `skb->len`、`gso_size`、`gso_segs`；
   - 本包扣减字节数、扣减前后 token；
   - 同一 skb/flow 是否在 fastpath 和 slowpath 各计一次。
2. 对比 `srcip` 与 `dstip` 相同流量下的累计扣减字节数；若下载约为实际转发字节的 2 倍，可直接确认重复计量。
3. 做 GRO/GSO A/B 测试：临时关闭 WAN 接收侧 GRO/GSO 后复测下载，观察 0.5 倍问题是否消失。
4. 用固定速率 UDP 做对照：
   - UDP 也约为配置值 50%：优先查 token/字节计量倍率；
   - UDP 接近配置值、仅 TCP 明显偏低：优先查 DROP policing 与 TCP 拥塞退避。
5. 若产品要求“配置多少、实测接近多少”，建议评估使用 HTB/fq 等队列整形替代纯 DROP policing；不建议简单把下载配置乘 2，这会掩盖内核计量问题并导致不同包长/协议下再次失准。

> 2026-07-29 补做 UDP 对照时，固定 iperf3 服务端被另一客户端 `192.168.148.4` 的多条会话持续占用，返回 `server is busy`。诊断规则已精确删除，IP_QOS 恢复 0 条；UDP 对照需待服务端释放后补充。

## 验收标准

1. IP/MAC × 独立/共享 × 上行/下行全部覆盖。
2. 单流和 4 流聚合实测均落在配置值 `±20%` 内。
3. TCP 和 UDP 均验证，不能只检查 iptables 规则存在。
4. 规则删除后数据库、IP_QOS/MAC_QOS、ipset 无残留。
5. 连续重复至少 5 轮，结果无固定 0.5 倍偏差。
