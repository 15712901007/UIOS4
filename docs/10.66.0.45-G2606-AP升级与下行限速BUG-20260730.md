## BUG-1：AC 智能控制模式 - AP版本升级 页面报错 `unknown TYPE (channel)`（四段式 JIRA）

### 标题
【IK-G2606-MXP 4.0.303】AC智能控制模式 无线服务-AP管理-AP版本升级 页面加载即报错 `unknown TYPE (channel)`，且 AP 最新版本无法获取

### 问题描述
进入「无线服务 → AP管理」（页面随即切换为 AC 智能控制模式视图）后，点击「AP版本升级」标签页，页面顶部立即弹出红色错误提示 `unknown TYPE (channel)`，每次进入必现。同时 AP 列表的「最新版本」列始终为 `--`（无法获取最新固件版本）。

经抓包与后端代码确认：**前端向 `/Action/call` 发送了一个后端从未实现的接口请求**
```
POST /Action/call
{"func_name":"ac_upgrade","action":"show","param":{"TYPE":"channel"}}
```
后端返回：
```
{"code":2007,"message":"unknown TYPE (channel)"}
```
前端将该 code:2007 当作错误用 message.error 弹出，即为用户看到的红色 `unknown TYPE (channel)`。

后端 `ac_upgrade` 接口的 show 分支只注册了 4 个 TYPE：`total` / `data` / `on_upgrade` / `upgrade_status`（见 `/usr/ikuai/script/ac_upgrade.sh` 的 `__show_total/__show_data/__show_on_upgrade/__show_upgrade_status`），**根本没有 `channel` 分支**。同接口的其它 TYPE 均正常：
- `TYPE=upgrade_status` → 正常返回升级状态
- `TYPE=total,data` → 正常返回 AP 列表（但 `new_version` 为空，故「最新版本」列显示 `--`）

即：**前端多发了一个后端不支持的 `TYPE=channel` 查询，属前后端接口协议不一致**（`channel` 应为升级通道/Beta 检测相关，后端尚未实现）。

### 复现步骤
1. 浏览器登录 http://10.66.0.45（admin/admin123）
2. 左侧菜单点击「无线服务」（页面自动进入 AC 智能控制模式，顶部出现“AC智能控制模式 / 关闭AC”）
3. 进入「AP管理」，点击「AP版本升级」标签页
4. 观察页面顶部提示与 AP 列表

### 实际结果
- 页面顶部弹出红色错误：`unknown TYPE (channel)`（每次进入必现）
- AP 列表「最新版本」列显示 `--`（IK-X2 当前版本 1.7.5，最新版本取不到）
- 接口层：`ac_upgrade show TYPE=channel` 返回 `code:2007 unknown TYPE (channel)`

### 预期结果
- 进入 AP版本升级 页面不应有任何错误提示
- 后端应正确处理 `TYPE=channel`（返回升级通道/Beta 检测状态），或前端移除该多余调用
- AP 列表「最新版本」列能正确显示该 AP 型号对应的最新可用固件版本

### 根因（开发参考）
- 前端：AP版本升级 页面组件加载时调用 `ac_upgrade action=show param.TYPE=channel`
- 后端：`/usr/ikuai/script/ac_upgrade.sh` 的 `show()` 经框架 `Show` 宏分发 TYPE，仅注册 total/data/on_upgrade/upgrade_status；`channel` 未注册 → 框架直接返回 `unknown TYPE (channel)`
- 全局搜索：`channel` 关键字仅出现在 `ac_group.sh`（且语义是无线 SSID 射频信道 channel:int 0-13 / channel_5g 0-165），与升级通道无关
- 修复方向：① 前端去掉 `TYPE=channel` 调用；或 ② 后端 ac_upgrade 补充 `channel` 分支实现（若为“Beta 升级检测/升级通道”新功能预留）

### 取证
- 接口抓包（浏览器 XHR 拦截）：
  - 请求 `{"func_name":"ac_upgrade","action":"show","param":{"TYPE":"channel"}}`
  - 响应 `{"code":2007,"message":"unknown TYPE (channel)"}`
- 控制台无 JS error（确认非前端异常，而是后端接口返回被当作错误展示）
- AC 控制器底层日志 `/tmp/log/ac.log.txt` 无此条（确认非 CAPWAP 守护进程层错误，而是上层接口层）

## BUG-2：终端限速（IP / MAC）下行限速值严重不准，实际仅约设定值的 55%

### 现象
对 client 192.168.148.2 配置下行限速，无论 IP 限速（终端限速/IP限速）还是 MAC 限速，**实际下行吞吐只有设定值的约 55%**，且伴随极高 TCP 重传。上行不限速时链路正常（926Mbps），排除链路问题。

### 复现步骤
1. client 侧先加临时路由（强制打流经 45，否则默认走直连不经过路由器）：
   ```
   sudo ip route add 10.66.0.40/32 via 192.168.148.1 dev ens11
   ```
2. Web 登录 10.66.0.45 → 网络配置 → 终端限速
3. **IP 限速**：新增规则，名称 test_ip_50m，内网地址 192.168.148.2，限速模式=独立限速，下行限速 3 MB/s（单位 MB/s），保存
4. client 测下行：`iperf3 -c 10.66.0.40 -R -t 10`（-R = 反向，server 发 client 收 = 下行）
5. **MAC 限速**：停用 IP 规则 → MAC限速 tab 新增规则，名称 test_mac_3m，MAC = D4:20:00:B1:45:EC，下行限速 3 MB/s，保存 → 测下行

### 实测数据（铁证）

| 限速类型 | 前端设定 | 后端 download | 理论下行 | 实际下行(receiver) | 实际/理论 | TCP 重传 |
|---|---|---|---|---|---|---|
| 不限速（基线，4线程） | — | — | — | **346 Mbps** | — | 570 |
| 不限速（上行单线程） | upload=0 | — | — | **926 Mbps** | — | 13 |
| IP 限速 | 3 MB/s | 3072 KB/s | 24.6 Mbps | **13.4 Mbps** | **54%** | 2109 |
| MAC 限速 | 3 MB/s | 3072 KB/s | 24.6 Mbps | **13.3 Mbps** | **54%** | 2050 |
| MAC 限速 | 6 MB/s | 6144 KB/s | 49.2 Mbps | **27.2 Mbps** | **55%** | 2742 |

> 换算：前端 MB/s × 1024 = 后端 download(KB/s)；download(KB/s) × 8 ÷ 1000 = 理论 Mbps。
> 单位下拉只有 KB/s / MB/s / GB/s（无 Mbps）。

**结论**：下行限速实际效果稳定为设定值的 ~55%，是固定系数偏差；重传随限速值增大而增多。

### 根因（开发参考）
下行限速（IP/MAC 共用）使用 ik_core 内嵌的自定义模块 `byteslimit`，以**硬 DROP** 方式限速，而非 HTB/tbf 整形：
```
# IP 限速
-A IP_QOS -m set --match-set simple_qos_1 dst -m ifaces ! --ifaces lan,vlan,... --dir in \
  -m timeset --timeset simple_qos_time_1 -m byteslimit --bytelimit 3072 --byteslimit-mode dstip -j DROP
# MAC 限速
-A MAC_QOS -m set --match-set mac_qos_1 dst ... -m byteslimit --bytelimit <N> --byteslimit-mode dstip -j DROP
```
- 机制：按目的 IP 统计字节，超过 `--bytelimit` 阈值直接 `-j DROP`（丢包，非排队延迟）
- 后果：DROP → TCP 大量重传 → 拥塞窗口退让 → 稳态吞吐被压到设定值约 55%（DROP/恢复振荡导致约 45% 吞吐损失）
- 对比：上行不限速单线程 926 Mbps、重传仅 13，证明链路与转发完全正常，问题在限速算法
- 修复方向：下行限速改用 HTB/tbf 整形（超限排队而非丢包），可准确达到设定值；或优化 byteslimit 的 burst/interval 参数降低 DROP 损失

### 复测方法（环境已保留）
当前保留两条限速规则（均在 网络配置→终端限速）：

| 规则 | 名称 | 对象 | 下行 | 状态 |
|---|---|---|---|---|
| IP 限速 id=1 | test_ip_50m | 192.168.148.2 | 3 MB/s | **启用** |
| MAC 限速 id=1 | test_mac_3m | D4:20:00:B1:45:EC | 3 MB/s | 停用 |

复测：
1. client 加路由：`sudo ip route add 10.66.0.40/32 via 192.168.148.1 dev ens11`（重启 client 后需重新加）
2. **测 IP 限速**（当前已启用，直接测）：`iperf3 -c 10.66.0.40 -R -t 10` → 预期 ≈ 13.4 Mbps
3. **测 MAC 限速**：Web 停用 IP 规则、启用 MAC 规则 → `iperf3 -c 10.66.0.40 -R -t 10` → 预期 ≈ 13.3 Mbps
4. **测基线**：Web 停用 IP 与 MAC 规则 → `iperf3 -c 10.66.0.40 -R -t 10` → 预期 远高于 100 Mbps
5. 测完若改限速值验证比例：Web 编辑下行值，重测（如 6 MB/s → 预期 ≈ 27 Mbps，仍为 55%）

> 备注：MAC 限速停用时其 iptables byteslimit 规则偶有残留（旧 bytelimit 值未刷新），但因 `mac_qos_1` ipset 为空不匹配，不影响实际生效（实测下行仍为 IP 限速的 13.4 Mbps，未被 MAC 残留规则干扰）。
